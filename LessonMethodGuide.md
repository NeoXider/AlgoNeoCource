# LessonMethodGuide

Краткие методические правила для авторов уроков: структура, практика, квизы и проверка нагрузки.

Если нужен именно синтаксис `quiz`, `check` или медиа, используйте [CourseTechGuide.md](CourseTechGuide.md) и папку `Docs/`.

## Рабочий порядок

1. Выберите курс: `course1.json`, `course2.json` или новый `courseN.json`.
2. Создайте урок в соответствующей папке `lessonsN/`.
3. Добавьте запись `{ id, title, file }` в JSON курса.
4. Соберите урок по стандартной структуре.
5. Проверьте урок в Unity через `Tools -> AlgoNeoCourse -> Open Course Window`.

## Базовая структура урока

Рекомендуемый порядок:

1. Введение
2. Теория
3. Практика
4. Перерыв
5. Теория
6. Практика
7. Итоги

Обязательные элементы:

- мотивация: зачем тема нужна в игре;
- `## Перерыв`;
- `## Итоги`.

Нормы полноценного урока:

- минимум 22 слайда;
- минимум 5 квизов;
- минимум 1 слайд `### 💡 Лайфхак`;
- один слайд должен содержать одну законченную мысль;
- длинную мысль делите на 2-3 коротких слайда.

## Как строить практику

Делите практику на два слоя: короткая проверка понимания и применение в Unity.

### Часть 1. Проверка понимания

Используйте `quiz`:

- после теории размещайте короткие вопросы;
- пояснение к ответу выносите на следующий слайд;
- после крупного теоретического блока добавляйте 1-2 вопроса;
- за урок должно получиться не меньше 5 квизов.

### Часть 2. Применение в проекте

Задание должно давать видимый результат в Unity:

- создать объект;
- добавить компонент;
- написать или изменить скрипт;
- связать это с текущей игровой механикой.

Если результат можно проверить автоматически, добавляйте `check`. Лучше несколько коротких шагов с отдельными проверками, чем одна большая задача.

## Правила для автопроверок

Проверки должны ловить суть задания, а не стиль кода.

Хорошая практика:

- проверять наличие файла, компонента, объекта, ключевого вызова;
- проверять `Debug.Log`, если важен сам факт вывода, а не точный текст;
- проверять наличие класса или метода, а не весь код построчно.

Плохая практика:

- требовать полное совпадение форматирования;
- завязываться на несущественные детали;
- требовать порядок строк или точный текст, если это не цель урока.

## Подача материала

### Теория

- давайте короткое объяснение;
- сразу показывайте маленький пример;
- связывайте теорию с игровым контекстом;
- не делайте абстрактную теорию без применения.

### Код в уроках

Обязательные правила (как в модулях m2–m4):

- **Планирование перед КАЖДЫМ блоком кода (всегда «сначала подумай»).** Никогда не показывайте код без рассуждения. На каждом слайде, где пишется код, СНАЧАЛА короткое живое рассуждение «что делаем и зачем это нужно объекту», и только потом сам блок ```csharp. Это приучает к программистскому мышлению.
  - Рассуждай от ЦЕЛИ к необходимости: «объект должен <уметь> → значит ему нужно <знать/хранить/делать> → заведём такое поле/метод». Опорная мысль: **компьютер не умеет догадываться — мы должны сказать ему явно**.
  - Дополнительно в начале сборки скрипта полезен обзорный `### Шаг 1: Планирование` (общий план: что понадобится), но он НЕ заменяет мини-рассуждение перед каждым конкретным куском кода.
  - Делай рассуждения ЖИВЫМИ и интересными: обращайся к ученику («давай подумаем», «что роботу нужно знать?»), маленькие понятные сравнения, лёгкий тон. Но коротко — 1–3 предложения, без стен текста, один слайд — одна мысль.
  - Пример: «Арбалет должен стрелять. А чем и откуда? Робот сам не угадает — подскажем ему: *чем* стрелять (`boltPrefab`) и *откуда* (`shootPoint`). Поэтому добавляем два поля.»
- **Без `namespace`.** В коде уроков всегда плоский класс (`public class X : MonoBehaviour`), без обёртки `namespace`. Namespace живёт только в эталонных `result-scripts`, ученику его показывать нельзя.
- **Дробите большой код на маленькие шаги.** Никаких «гигантских» блоков. Один шаг `### Шаг N` = одна маленькая часть: сначала пустой класс, потом отдельным шагом поля, потом отдельным шагом каждый метод (например поворот, выстрел, перезарядка — три разных шага). Ориентир: один блок ```csharp ≤ ~20 строк.
- **Комментарии в коде обязательны.** Короткий `//` над каждым методом и над неочевидными строками (стиль m2, например `// Вызывается каждый кадр`, `// уменьшаем здоровье`). Не комментируйте очевидное до абсурда.
- **Не дампите «готовый скрипт целиком»**, если он больше ~20 строк — пошаговая сборка уже показала весь код. Маленький финальный блок для сверки допустим.
- **Не делайте шаг «создать пустой класс».** При создании скрипта Unity уже добавляет класс с `Start()` и `Update()`. Шага «создайте скрипт `X.cs`» достаточно — дальше сразу дополняйте класс полями и методами, не показывая пустой `public class X : MonoBehaviour { }`.
- **Не объясняйте повторно** команды и свойства, уже изученные в прошлых модулях — используйте их сразу («уже знакомо по прошлым модулям»). Подробно разбирайте только то, что появляется впервые в этом модуле.
- Весь C# ориентирован на Unity; новый концепт сопровождайте коротким рабочим фрагментом и узнаваемыми примерами (`Start()`, `Update()`, `Debug.Log()`, компоненты, объекты сцены).

### Визуальное оформление

- не делайте стены текста;
- используйте изображения только там, где они реально помогают;
- полезный совет оформляйте отдельным слайдом `### 💡 Лайфхак`;
- минимум один лайфхак обязателен.

### Блок `>` для пояснений

Используйте `>` для пошаговых разборов:

- после кода, где 3+ действия;
- после нового оператора или конструкции: `!`, `&&`, `||`, `==`, `? :`;
- когда нужно сравнить новую конструкцию с уже знакомой;
- перед практикой, где ученик собирает итоговую логику.

Пример структуры:

```markdown
> **Как работает (по шагам):**
> 
> 1. Метод принимает...
> 2. Выражение проверяет...
> 3. Результат возвращается через...
```

или для кода:

```markdown
> **Как выглядит итоговый код (по шагам):**
> 
> ```csharp
> public bool IsValid(int x) { return x > 0; }
> ```
> 
> 1. Метод принимает число x
> 2. Проверяется условие x > 0
> 3. Результат (true/false) возвращается в вызывающий код
```

## Методические ограничения

- в практике используйте только то, что уже объяснили или прямо подготовили на текущем слайде;
- не требуйте методы, свойства, типы, переменные или конструкции, которые ещё не объяснялись;
- не смешивайте много новых концептов в одной задаче;
- вопросы должны проверять изученное, а не угадывание;
- `check` и шаги задания не должны подталкивать к ещё не разобранному коду;
- задания должны вести к ощутимому игровому результату.

## Перед публикацией урока

Проверьте:

- урок добавлен в правильный JSON курса;
- `file` указывает на реальный `.md`;
- структура урока выдержана;
- квизы распределены по ходу материала, а не свалены в один блок;
- практики имеют понятный ожидаемый результат;
- есть `## Перерыв`, `## Итоги`, минимум 22 слайда, 5 квизов и 1 лайфхак;
- финальный слайд `## Итоги` присутствует.

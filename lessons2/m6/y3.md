# Модуль 6, Урок 3: GameManager, очки и Game Over

**Цель урока:** завести в игре одного «главного» — `GameManager`, показать счёт на экране и научить игру заканчиваться.

Корабль летает, стреляет, астероиды падают и исчезают от попадания. Механики есть — игры пока нет: очки нигде не считаются, а столкновение с астероидом ничем не заканчивается.

Сегодня превращаем набор механик в игру, у которой есть результат.

---

## Кто в игре считает очки?

Астероид взорвался. Кто должен прибавить 10 очков?

- Сам астероид? Через миг он исчезнет вместе со всеми своими данными.
- Пуля? Она тоже исчезает.
- Корабль? Он занят движением и стрельбой.

Нужен кто-то, кто живёт всю партию целиком и помнит общее состояние игры.

---

## Что появится в игре сегодня

- объект `GameManager` со скриптом `GameManager.cs`;
- надпись `ScoreText` со счётом в углу экрана;
- панель `GameOverPanel` с надписью «Игра окончена»;
- остановка игры после столкновения с астероидом.

К концу урока игру можно будет проиграть. Звучит грустно, но именно с этого момента в неё становится интересно играть.

---

## Теория 1: у общего состояния — один владелец

`GameManager` вы уже заводили в Tower Defence: он хранил монеты и знал, сколько их у игрока. Здесь его работа ровно та же, только вместо монет — счёт и флаг «игра окончена».

И причина та же. У каждого объекта своя маленькая работа, и никто из них не живёт всю партию: астероид взрывается, пуля исчезает, а счёт должен пережить их всех. Значит, договорённость прежняя:

- **никто** не трогает счёт напрямую;
- все вызывают у менеджера `AddScore(10)`;
- о проигрыше сообщают через `FinishGame()`.

Новое в этом уроке ровно одно: как **закрыть счёт от чужих рук**, чтобы правило «счёт меняется только через `AddScore`» нельзя было обойти даже случайно.

## Пояснение (одна дверь для изменений)

- Один метод `AddScore` — одно место, где можно проверить `IsGameOver` и обновить надпись.
- Если завтра появится звук «плюс очки», его тоже нужно будет добавить ровно в одну строку.
- А если счёт меняют пять скриптов, то и баг «очки иногда скачут» придётся искать в пяти местах.

---

## Как разрешить читать счёт всем, а менять — только менеджеру?

Счёт должен видеть весь проект: его показывает UI, его может спросить любой скрипт.
Но менять его должен уметь только сам `GameManager`.

Обычное поле такую задачу не решает:

```csharp
public int Score;
```

Если написать так, любой скрипт сможет сделать `gameManager.Score = 9999;` — и правило «счёт меняется только через `AddScore`» развалится в первый же день.

А если написать `private int score;`, счёт станет невидимым даже для тех, кому просто нужно его прочитать.

---

## Теория 2 (1/3): свойство — это окно, а не дверь

В C# есть конструкция ровно под эту задачу — **свойство**:

```csharp
// Счёт: читать может любой скрипт, менять — только сам GameManager
public int Score { get; private set; }
```

Снаружи `Score` выглядит и используется как обычная переменная: `gameManager.Score`.
Но внутри фигурных скобок мы отдельно задали правила на чтение и на запись.

> **Как читать эту запись по частям:**
>
> 1. `public` — обращаться к `Score` можно из любого скрипта.
> 2. `get` — «взять значение» разрешено всем.
> 3. `private set` — «положить значение» разрешено только внутри класса `GameManager`.
> 4. Значит строка `Score += points;` работает внутри менеджера и не компилируется снаружи.

Обычное поле — дверь нараспашку: заходи кто хочет.
Свойство `{ get; private set; }` — окно: смотреть можно всем, а ручка только с внутренней стороны.

---

## Теория 2 (2/3): как это пишется (и где все ошибаются)

Смысл понятен. Теперь про буквы — именно здесь спотыкается почти весь класс.

```csharp
public int Score { get; private set; }
public int Lives { get; private set; } = 3;
```

Три правила записи:

1. **Внутри фигурных скобок точки с запятой есть** — и после `get`, и после `set`. Это не одна строка кода, а два отдельных разрешения, каждое со своей точкой с запятой.
2. **После закрывающей фигурной скобки точки с запятой нет.** Исключение ровно одно: если сразу задаём стартовое значение через `=`, тогда точка с запятой ставится в самом конце, после числа — как в строке с `Lives`.
3. **Свойство пишут с заглавной буквы, поле — с маленькой.** Сравните: `Score` — свойство, `scoreText` — поле. Это общая договорённость C#, и наши автопроверки ждут именно `Score`.

Ошиблись — Visual Studio подчеркнёт лишнюю или пропущенную точку с запятой красным прямо в строке. Обе ошибки лечатся одним символом, так что пугаться нечего.

---

## Теория 2 (3/3): важное ограничение — свойств нет в инспекторе

Unity показывает в инспекторе только **поля**. Свойства он не рисует никогда, даже публичные.

Поэтому у нас будет простое правило выбора:

- значение считает сама игра (счёт, флаг «игра окончена») -> **свойство** `{ get; private set; }`;
- значение хочется крутить мышкой (скорость, интервалы, темп спавна) -> **поле** `[SerializeField] private`.

Ошибиться легко: написали свойство, полезли в инспектор — а поля нет, и кажется, что скрипт сломался. Он не сломался, просто свойства там не показываются.

- `get` открывает чтение всем, `private set` оставляет запись только внутри класса.

- А вот `gameManager.Score = 100;` компилятор запретит — и это именно то, чего мы хотели.

## Практика 1: Экран, который показывает результат

Сначала соберём то, что увидит игрок: надпись со счётом и панель проигрыша. Код подключим к ним следующей практикой.

### Шаг 1: Создайте Canvas и текст счёта

1. В `Hierarchy` нажмите правой кнопкой мыши -> `UI` -> `Canvas`. Рядом Unity сам создаст объект `EventSystem` — не удаляйте его, он понадобится кнопкам.
2. Нажмите правой кнопкой на `Canvas` -> `UI` -> `Text - TextMeshPro`. Если Unity предложит `Import TMP Essentials`, нажмите кнопку импорта: это разовая установка шрифтов.

4. Выделите `ScoreText`. В `Inspector` в компоненте `TextMeshPro - Text (UI)`:
   - `Text Input`: напишите `Очки: 0`;
   - `Font Size`: `36`;
   - `Alignment`: по левому краю и по верху.
5. В `Rect Transform` нажмите на квадрат с якорями (слева вверху компонента) и, удерживая `Shift + Alt`, выберите **верхний левый** вариант. Теперь надпись прилипнет к левому верхнему углу экрана при любом разрешении.
6. Поставьте `Pos X`: `140`, `Pos Y`: `-40`.

### 💡 Лайфхак: не выключайте руками то, чем управляет код

Пока настраиваете внешний вид `GameOverPanel`, держите её **включённой** — иначе вы просто не увидите, что делаете.

Общее правило: если состоянием объекта управляет код, не трогайте это состояние руками — иначе вы будете спорить со своей же программой и не поймёте, кто прав.

### Шаг 2: Добавьте то, что менеджер знает

Куда писать счёт? Менеджер не угадает — дадим ему ссылку на надпись. Какую панель показать при проигрыше? Тоже ссылку. Эти две вещи мы перетаскиваем мышкой, значит это поля с `[SerializeField]`.

А ещё ему нужно помнить сам счёт и то, закончилась ли игра. Эти два значения считает сама игра — значит это свойства.

Откройте `GameManager.cs` и **замените его содержимое целиком** на такое:

```csharp
using TMPro;
using UnityEngine;

public class GameManager : MonoBehaviour
{
    [Header("Настройки")]
    [SerializeField] private TMP_Text scoreText;
    [SerializeField] private GameObject gameOverPanel;

    public int Score { get; private set; }
    public bool IsGameOver { get; private set; }
}
```

`[Header("Настройки")]` — знакомая по прошлому уроку подпись: она отделяет в инспекторе два поля, которые заполняем мышкой. Свойств в инспекторе не будет вообще.

Точки с запятой: внутри фигурных скобок есть, после закрывающей — нет. Ровно тот случай из Теории 2 (2/3).

```check

  - contains: "using TMPro"
  - contains: "public class GameManager"
  - contains: "[SerializeField] private TMP_Text scoreText"
  - contains: "[SerializeField] private GameObject gameOverPanel"
  - contains: "public int Score { get; private set; }"
  - contains: "public bool IsGameOver { get; private set; }"
```

### Шаг 3: Научите менеджер начислять очки

Сразу два метода, потому что они бесполезны друг без друга.

Первый — маленький переводчик из числа в надпись на экране. Наружу его открывать незачем, им пользуется только сам менеджер, значит `private`.

Второй — та самая «касса». Астероид не трогает `Score` сам: он приходит и просит начислить, а менеджер сначала смотрит, не закончилась ли игра. Ранний `return` уже знаком по прошлым модулям.

```csharp
// Переписывает надпись на экране текущим счётом
private void UpdateScoreText()
{
    scoreText.text = "Очки: " + Score;
}

// Вызывается снаружи, когда игрок что-то уничтожил
public void AddScore(int points)
{
    if (IsGameOver)
    {
        return;
    }

    Score += points;
    UpdateScoreText();
}
```

> **Как работает по шагам:**
>
> 1. Метод принимает число `points` — сколько очков добавить.
> 2. Если `IsGameOver` уже `true`, метод молча выходит и ничего не меняет.
> 3. `Score += points` — единственное место во всём проекте, где счёт растёт.
> 4. `UpdateScoreText()` сразу переписывает надпись, поэтому обновлять её каждый кадр не нужно.

```check
rules:
  - filename: "GameManager.cs"
  - contains: "public void AddScore(int points)"
  - contains: "Score += points"
  - contains: "UpdateScoreText()"
  - contains: "scoreText.text"
```

### Шаг 4: Добавьте завершение игры

Проигрыш должен случиться ровно один раз. Если в один кадр в корабль врежутся сразу два астероида, метод вызовется дважды — а панель не должна включаться повторно.

Спасает та же защита ранним `return`, что и в `AddScore`.

```csharp
// Вызывается, когда корабль столкнулся с астероидом
public void FinishGame()
{
    if (IsGameOver)
    {
        return;
    }

    IsGameOver = true;
    gameOverPanel.SetActive(true);
}
```

Обратите внимание: менеджер не останавливает корабль и не выключает спавнер. Он просто поднимает флаг `IsGameOver`. Кто хочет — тот и посмотрит на этот флаг. Так менеджеру не нужно знать про все объекты сцены.

```check
rules:
  - filename: "GameManager.cs"
  - contains: "public void FinishGame()"
  - contains: "IsGameOver = true"
  - contains: "gameOverPanel.SetActive(true)"
```

## Если появилась NullReferenceException

Скорее всего Unity покажет ошибку в строке:

```csharp
scoreText.text = "Очки: " + Score;
```

Проблема не в тексте `"Очки: "`. Проблема в том, что стоит **до точки**: `scoreText` ни на что не указывает.

Проверьте в `Inspector` у объекта `GameManager`:

- поле `Score Text` заполнено, и в нём лежит именно `ScoreText` с компонентом TextMeshPro;
- поле `Game Over Panel` тоже заполнено — если забыть его, ошибка прилетит уже из строки `gameOverPanel.SetActive(false)`;
- в поле `Game Over Panel` перетащена сама панель, а не текст внутри неё.

Общее правило: `NullReferenceException` почти всегда означает «пустое поле в инспекторе», а не ошибку в коде.

## Как астероид найдёт менеджера?

С кораблём и спавнером всё просто: они лежат на сцене, можно выделить их и перетащить `GameManager` мышкой в нужное поле.

С астероидом так не выйдет. Астероида на сцене нет — он рождается во время игры из префаба. Перетащить ссылку в объект, которого ещё не существует, невозможно.

Значит, ссылку должен вписать тот, кто астероид создаёт, — спавнер. Прямо в момент рождения.

## Теория 3: спавнер выдаёт ссылку прямо при рождении

Приём знакомый по спавнеру Tower Defence: там вы уже писали `EnemyUnit enemy = Instantiate(enemyPrefab, ...);` и следующей строкой `enemy.gameManager = gameManager;`. У нас будет один в один то же самое:

```csharp
AsteroidMover asteroid = Instantiate(asteroidPrefab, position, Quaternion.identity);
asteroid.gameManager = gameManager;
```

Работает это за счёт двух вещей: `Instantiate` возвращает созданный объект, а поле префаба объявлено не как `GameObject`, а сразу типом скрипта — `[SerializeField] private AsteroidMover asteroidPrefab;`. Поэтому и возвращается готовый `AsteroidMover`, без `GetComponent`.

Действительно новое здесь одно: почему поле у астероида объявлено как `public GameManager gameManager;`, а не привычным `[SerializeField] private`. Потому что заполняет его **не человек мышкой, а другой скрипт кодом**. В приватное поле спавнер записать не сможет — компилятор не даст.

> ⚠️ **Важно:** как только вы поменяете тип поля с `GameObject` на `AsteroidMover`, ссылка в инспекторе **опустеет**. Unity не умеет переносить значение в поле другого типа. Это не поломка — просто перетащите префаб `Asteroid` в поле `Asteroid Prefab` заново.

## Пояснение (кто заполняет ссылку)

- Объекты сцены настраиваются мышкой заранее — для них удобно `[SerializeField] private`.
- Объекты, которые рождаются во время игры, настраивает тот, кто их создал.
- Отсюда простое правило: `private` — «настраиваю я», `public` — «заполняет другой скрипт».

## Практика 3: Связка «астероид — менеджер»

Теперь научим астероид начислять очки и заканчивать игру.

### Шаг 1: Обновите поля астероида

Что теперь нужно знать астероиду? Сколько очков он стоит и кому эти очки отдать.

И ещё одна деталь: его скорость перестаёт быть «просто скоростью». На финальном уроке менеджер начнёт её умножать, разгоняя игру, поэтому уже сейчас переименуем `speed` в `baseSpeed` — это **базовая** скорость, к которой позже добавится множитель.

⚠️ **Замените** оба существующих поля (`speed` и `destroyY`) вот этим блоком целиком. Не дописывайте его снизу — иначе `destroyY` будет объявлен дважды и проект не соберётся.

```csharp
[SerializeField] private float baseSpeed = 3f;
[SerializeField] private float destroyY = -6f;
[SerializeField] private int scoreValue = 10;

// Заполняет не человек в инспекторе, а спавнер в коде
public GameManager gameManager;
```

Переименование Unity переживает так же, как смену типа: старое значение `Speed` у префаба `Asteroid` пропадёт, и в новое поле `Base Speed` встанет `3` из кода. Правило общее и без исключений — **поменяли у поля имя или тип, сразу загляните в инспектор и проверьте значение**.

Не забудьте поправить строку движения в `Update()` — поля `speed` там больше нет:

```csharp
transform.position += Vector3.down * baseSpeed * Time.deltaTime;
```

### Шаг 2: Начислите очки за попадание

Попадание пули у нас уже обрабатывается — осталось добавить один вызов.

```csharp
if (other.GetComponent<ProjectileMover>() != null)

    Destroy(gameObject);

}
```

```csharp
private void SpawnAsteroid()
```

## Почему прямо сейчас Game Over не наступит

Логику проигрыша мы вот-вот напишем, но есть подвох, из-за которого она молча не заработает.

Вспомните правило из прошлых уроков: чтобы `OnTriggerEnter2D` сработал, нужны коллайдеры у **обоих** объектов, `Is Trigger` хотя бы у одного и `Rigidbody2D` хотя бы у одного.

Пуля и астероид этому правилу уже соответствуют — мы настраивали их в первом и втором уроках. А вот корабль до сих пор не участвует в физике вообще: у `Player` нет ни коллайдера, ни `Rigidbody2D`. Он просто картинка, которую двигает скрипт.

Поэтому астероид пролетает сквозь корабль, и никакого сообщения о столкновении не приходит. Самое неприятное здесь то, что `Console` при этом абсолютно чистая: ошибки нет, просто ничего не происходит.

Значит, следующий шаг — дать кораблю тело. И обязательно `Kinematic`, иначе он начнёт падать вниз от гравитации и отлетать от каждого удара.

## Пояснение (что даёт кораблю каждая настройка)

- Коллайдер задаёт форму: без неё физике просто нечего пересекать.
- `Rigidbody2D` включает объект в расчёт физики — без него пара коллайдеров игнорируется.
- `Kinematic` оставляет тело «физическим», но убирает гравитацию и толчки: позицией управляет только наш скрипт.
- А `GameManager` к столкновению отношения не имеет: он узнаёт о нём уже потом, из вызова `FinishGame()`.

## Практика 3 (продолжение): корабль вступает в игру

### Шаг 4: Настройте корабль для столкновений

1. Выделите `Player` в `Hierarchy`.
2. Нажмите `Add Component` -> найдите `Box Collider 2D`.
3. В компоненте `Box Collider 2D` поставьте галочку **`Is Trigger`**.
4. Посмотрите на окно `Scene`: зелёная рамка коллайдера должна примерно совпадать с кораблём — Unity подогнала её под спрайт в момент добавления. Если рамка от другой картинки (вы меняли спрайт после), нажмите правой кнопкой по компоненту `Box Collider 2D` -> `Reset`. Точнее подогнать края можно кнопкой `Edit Collider` или полем `Size`.
5. Нажмите `Add Component` -> найдите `Rigidbody 2D`.
6. В компоненте `Rigidbody 2D` в поле `Body Type` выберите **`Kinematic`**.

> **Как это работает вместе:**
>
> 1. `Box Collider 2D` задаёт форму корабля для физики.
> 2. `Is Trigger` говорит: «не отталкивай, просто сообщи о касании».
> 3. `Rigidbody 2D` включает корабль в физический мир — без него касание никто не заметит.
> 4. `Kinematic` убирает гравитацию и толчки: позицией управляет только `PlayerShipController`.

### Шаг 6: Остановите корабль после проигрыша

Панель появилась, а корабль всё ещё летает и стреляет сквозь неё. Игра «на паузе» должна выглядеть как пауза.

```csharp
[SerializeField] private GameManager gameManager;
```

```csharp
void Update()
{
    // После проигрыша корабль не двигается и не стреляет
    if (gameManager != null && gameManager.IsGameOver)

}
```

## Если очки не растут, а ошибок нет

Самая коварная поломка урока выглядит так: игра идёт, астероиды взрываются, а `Console` абсолютно чистая. Виновата наша же защита `if (gameManager != null)` — она спасает игру от падения, но заодно съедает единственное сообщение об ошибке.

Поэтому ищем по симптому:

- **Счёт стоит на нуле.** У объекта `Spawner` пустое поле `Game Manager` — астероиды рождаются без телефона менеджера.
- **Счёт не растёт даже после того, как вы заполнили поле.** Астероиды, которые уже летят по экрану, ссылку не получили: она выдаётся только в момент рождения. Остановите и снова запустите `Play`.
- **Корабль летает и стреляет после `Игра окончена`.** Пустое поле `Game Manager` у объекта `Player`.
- **Панель проигрыша не появляется.** Пустое поле `Game Over Panel` у `GameManager` — вот здесь как раз будет честный `NullReferenceException` в `Console`.

Общее правило: **если поведение пропало, но `Console` молчит — ищите пустое поле там, где в коде стоит проверка `!= null`.**
